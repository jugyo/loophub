SYSTEM DESIGN

Workspace 設計 — Git ブランチを実体とする作業スペース

Git ブランチを workspace の実体とし、issue と PR の base branch を一貫して管理する設計

workspace-design.ja.md 2026-07-17 ~14 分で読了

1. 現状の整理(設計の土台)

workspace の中核 3 要素は、いずれも既にコードに存在する。ここで確認するのは、実装を進める前に必要な既存メカニズムの認識である。

要素既存実装場所
issue ↔ ブランチの関連付けissues.target_branch カラム(nullable)。issue 作成時に指定でき、assertExistingLocalBranch で既存ローカルブランチであることを検証するcore/db.ts:144、core/service/issues.ts、core/service/shared.ts
PR base の決定lh build(dev.openPr)と pulls.create の両方が 既存 PR の base → 明示 base 指定 → issue.target_branch → repo.default_branch の優先順位で base を決める。明示指定を CLI に公開するのは lh pr create --base のみcore/service/dev.ts:143-147、core/service/pulls.ts:164
リポジトリトップのブランチ別表示issue list は既に target_branch で issue をグルーピングし、デフォルトブランチのセクションを先頭に、ブランチ名を <h2> 見出しとして表示しているweb/src/components/issue-list.tsx:52-83, 120-124, 372-391

さらに、worktree provisioning は PR の base_ref / base_sha を分岐元として使い、並行 attempt は先行 PR の base_sha を継承する。つまり workspace ブランチを base とした build / attempt / merge / conflict 検出は、issue.target_branch が設定されてさえいれば今日すでに end-to-end で動く。

本設計の対象

欠けているのは 3 点のみである。①空の workspace を表現できない、②ブランチ作成 + workspace 登録を 1 操作で行う UI がない、③セクションごとの New issue ボタンと自動引き継ぎがない。本設計はこの 3 点に閉じる。

2. ドメイン用語(仮称の決定を含む)

用語定義
Workspaceデフォルトブランチとは別の統合先となる ローカル git ブランチを実体とする作業スペース。複数の issue(とその PR / attempt)を同じブランチ上に積み上げるための単位。実体はブランチであり、LoopHub 側の row は「このブランチは workspace である」という登録情報にすぎない
Workspace ブランチworkspace の実体であるローカルブランチ。命名は自由(強制プレフィクスなし)。デフォルトブランチと同名は不可
Workspace issuetarget_branch が workspace ブランチを指す issue。その issue から作る PR の base は workspace ブランチになる
識別(repo_id, branch) の組で一意。workspace 名 = ブランチ名であり、別名(表示名)は持たない
作成時の起点デフォルトブランチのその時点のローカル HEAD。fetch はしない

仮称 workspace をそのまま採用する。このコードベースには既に近い用語が 2 つあるが、ドメインが異なるため共存させる。

  • herdr workspace: ターミナル統合(herdr)の UI コンテナ。ドメインが違う(ターミナル UI vs ブランチ)ため、コード内のコメント・識別子では herdr 側を常に herdr workspace と限定修飾する
  • worktree: PR/attempt 専用の git linked checkout(loophub/pr-<m>)。workspace は「統合先ブランチ」であり checkout を持たない

3. データモデル

workspace の状態は workspaces という軽量レジストリで管理される。git が実体であり、DB は登録簿という既存方針と同じ構図である。

CREATE TABLE IF NOT EXISTS workspaces (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  repo_id     INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  branch      TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  archived_at TEXT,                -- NULL = active。soft archive(ブランチには触れない)
  UNIQUE (repo_id, branch)
);

追加は CREATE TABLE IF NOT EXISTS の追記のみ。ブランチの存在は保存しない。表示時に git へ問い合わせて導出する(git worktree list と DB の PR/session 情報を真実にし、別台帳を持たないという既存方針の workspace 版)。issue との関連付けカラムは持たない。関連は issues.target_branch = workspaces.branch という値の一致で導出する。

要点

issue 側はスキーマ変更ゼロ。PR base 決定も既存コードのまま動く。repos テーブルと同じ構図で理解しやすい

export interface WorkspaceWire {
  branch: string;
  created_at: string;
  archived_at: string | null;
  branch_exists: boolean;  // 表示時に git から導出
}

5. workspace の作成フロー

リポジトリトップの filter bar に New workspace ボタンを置く。押すとダイアログを開く。

core/service/workspaces.ts(新設)に core service を実装する。CLI と RPC の両方から使う。

  1. create(repo, { branch }): ブランチ名検証、registry 重複判定(active/archived)、git branch 作成、INSERT
  2. list(repo): active な registry rows を返し、各 row の branch_exists を localBranchExists で導出
  3. archive(repo, branch) / unarchive(repo, branch): archived_at の set/clear。ブランチは削除しない

エラーハンドリング

失敗はすべて ServiceError で返し、リトライ・自動補修は入れない。RPC の error message をダイアログ内にそのまま表示する

6. PR / attempt の base branch 引き継ぎルール

workspace issue から作られる PR / attempt の base は、常にその issue の target_branch(= workspace ブランチ)である。これは新規実装ではなく、既存の優先順位の確認と明文化である。

経路挙動(すべて既存実装)
lh build <issue> → dev.openPr既存 open PR の base_ref → input.base 引数 → issue.target_branch → repo.default_branch。workspace issue なら workspace ブランチが base になり、その時点の HEAD が base_sha に記録される
lh pr create同じ優先順位。--base の明示指定は workspace より優先される
worktree provisioningPR の base_ref / base_sha から分岐。loophub/pr-<m> は workspace ブランチから fork する
並行 attempt(--new-attempt)先行 PR の base_sha を継承。workspace 配下でも「同じ fork 元」の公平比較が成立
merge / conflict 検出 / workflow runすべて pull.base_ref を読む。workspace ブランチが base の PR は workspace ブランチへ merge される

鮮度の方針

PR の fork 元は「build 時点の workspace ブランチ HEAD」。workspace ブランチが先に進んでも既存 PR の base_sha は動かさない。陳腐化は既存の conflict sweep と commits_ahead 表示に委ねる

7. workspace 配下への issue 作成

New issue は現在、Herdr セッションを起動して issue-create スキルを実行する方式。workspace 版も同じ経路に乗せ、target branch を 1 本の紐で末端まで通す。

  1. UI: workspace セクションの New issue ボタンは targetBranch: string prop 付きで CreateIssueButton を再利用
  2. RPC → command: terminal.launch の入力に targetBranch?: string を追加し、lh issue new --repo <repo> --target-branch <branch> を組み立てる
  3. lh issue new: --target-branch フラグを受け取り、スキルセッションへ環境変数(LOOPHUB_WORKSPACE)で渡す
  4. CLI → 永続化: 通常の lh issue create は明示的な --target-branch がなければ LOOPHUB_WORKSPACE を使う

取得について

新設 API を作らない。issue list の応答(IssueWire.target_branch)を registry(workspaces/list)と突き合わせてクライアント側でグルーピングする

8. 互換性・移行方針

本設計は 後方互換とデータ移行を考慮しない。したがって、workspace は追加機能であり、registry が空なら repo トップは default セクションのみになる。

  • 既存 issue / PR / デフォルトブランチ向けフローとの互換維持は設計目標にしない。target_branch は workspace フロー経由でのみ設定される、というクリーンスレート前提で組む
  • DB は workspaces テーブルを新設するのみ。既存 row の migration・backfill は行わない
  • 既存ブランチを workspace として取り込む導線(adopt)は持たない

9. 責務境界(core / DB / serializer / CLI / RPC / Web UI)

層追加・変更

JSON-RPC(web/server/contract.ts)workspaces/create / workspaces/list / workspaces/archive

設計原則

ドメインロジック(git + DB をまたぐ判断)はすべて core service に置き、CLI / RPC は薄く保つ
