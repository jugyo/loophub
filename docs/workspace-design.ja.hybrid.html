Git ブランチを実体とする作業スペース

workspace-design.ja.md 2026-07-16 ~14 分で読了

設計の土台

要点

workspace の実体は git ブランチそのもの。LoopHub は workspaces registry に登録して UI に出すだけで、issue との関連は既存 issues.target_branch、PR base は既存の 明示 base > issue.target_branch > repo.default_branch を再利用する。新しい紐づけ機構は作らない。

リポジトリトップでデフォルトブランチとは別の統合先ブランチを workspace として作成・表示し、その配下に issue をぶら下げる。issue から作る PR の base branch は workspace ブランチへ一貫して向ける。起票 issue は #1352。実装は後続 issue に分割する。

要素既存実装場所
issue ↔ ブランチnullable な issues.target_branch。作成時に指定、assertExistingLocalBranch または ensureLocalBranchFromDefault（create_target_branch）で検証・作成core/db.ts:144、core/service/issues.ts:163-175、core/service/shared.ts:392-439
PR baselh build（dev.openPr）と pulls.create が既存 PR base → 明示 base → issue.target_branch → repo.default_branch で決定。CLI の明示 base は lh pr create --base のみcore/service/dev.ts:143-147、core/service/pulls.ts:164
ブランチ別表示issue list は target_branch でグループ化し、default を先頭、ブランチ名を <h2> で表示web/src/components/issue-list.tsx:52-83, 120-124, 372-391

worktree provisioning は PR の base_ref / base_sha を分岐元として使い（core/worktree-provision.ts:129-146、呼び出し側 cli/commands/build.ts:270-288）、並行 attempt は先行 PR の base_sha を継承する（core/service/dev.ts:130-133,162、parallel-issue-attempts-design.ja.md）。target_branch が設定済みなら workspace base の build / attempt / merge / conflict 検出は end-to-end で既に動く。

  1. 名前付き workspace の存在：issue が 0 件でも表現する。現在の表示は open issue の target_branch から導出するため 0 件で消える。
  2. リポジトリトップからの作成導線：現状は lh issue create --target-branch --create-target-branch の副作用のみ。
  3. workspace 配下への issue 作成導線：セクションごとの New issue と target_branch 自動引き継ぎ。

ドメイン用語と名称

用語定義
Workspaceデフォルト以外の統合先となるローカル git ブランチを実体とする作業スペース。複数 issue と PR / attempt を同じブランチ上に積む。LoopHub row は workspace 登録情報だけ。
Workspace ブランチworkspace の実体。命名自由・強制プレフィクスなし・default と同名不可。
Workspace issuetarget_branch が workspace ブランチを指す issue。PR base はそのブランチ。
識別(repo_id, branch) で一意。workspace 名はブランチ名で別名なし。
作成時の起点デフォルトブランチのその時点のローカル HEAD。fetch しない（lh-build-worktree.ja.md の base 鮮度方針と同じ）。

名称は workspace

GitHub 等で「作業の置き場」として通用し、#1352 の仮称でもあるため正式採用する。実装 issue で AGENTS.md Glossary に追記する。

✓ 長所

  • workspace は作業単位の名前として自然で、ブランチ実体を説明できる。
  • herdr workspace とドメインが異なるため共存できる。

✕ 短所

  • herdr workspace は terminal UI コンテナ（core/service/terminal.ts:511-553、herdr workspace create）のため、新規・変更コードのコメントと識別子では常に herdr workspace と限定する。既存 terminal 系の一括 rename はしない。
  • worktree は PR/attempt 専用 linked checkout（loophub/pr-<m>）。workspace は checkout を持たず、workspace 1 : PR worktree 多の関係。

記録した代替名は workstream（衝突なしだが馴染みが薄い）、branch group（表示説明で作業単位名でない）、epic（issue 階層を連想しブランチ実体から遠い）。

データモデル

CREATE TABLE IF NOT EXISTS workspaces (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  repo_id INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  branch TEXT NOT NULL,
  created_at TEXT NOT NULL,
  archived_at TEXT, -- NULL = active。soft archive（ブランチには触れない）
  UNIQUE (repo_id, branch)
);
  • core/db.ts の毎 boot 実行に沿って CREATE TABLE IF NOT EXISTS を追記。後方互換・移行・既存 row backfill は対象外。
  • ブランチ存在は保存せず表示時に git から導出する。git worktree list と DB の PR/session 情報を真実にし別台帳を持たない既存方針の workspace 版。
  • issue 関連カラムを持たず、issues.target_branch = workspaces.branch の一致で導出する。

案 A: registry なし（不採用）

workspace/ プレフィクスのブランチを workspace とみなす。空 workspace は表現できるが任意名を扱えず、archive 等の LoopHub 側状態の置き場がない。

案 B: 軽量 registry + target_branch 再利用

§3.1 のテーブルで空 workspace・作成日時・archive を表現。issue はスキーマ変更ゼロで、既存 PR base 決定もそのまま動く。repos と同じ「git が実体、DB は登録簿」の構図。

案 C: first-class 参照

issues.workspace_id FK または join table。整合性は強いが target_branch を読む既存経路すべてで二重管理と同期が生じる。関連メタデータの要求が固まるまで導入しない。

案 B はモデルを最小にする。弱点は git 外部 rename に registry と target_branch が追従しないことだが、案 C でも検知はできない。missing branch として可視化し、追従操作は将来課題とする。

export interface WorkspaceWire {
  branch: string;
  created_at: string;
  archived_at: string | null;
  branch_exists: boolean; // 表示時に git から導出
}

core/serialize.ts に wire SSOT として追加し、web/ は type-only import で消費する。IssueWire.target_branch は既存のため issue wire は変更しない。

PR / attempt の base 引き継ぎ

要点

workspace issue の PR / attempt base は常に issue.target_branch（workspace ブランチ）。これは新規実装ではなく既存優先順位の明文化。

経路既存挙動
lh build <issue>既存 open PR base_ref → input.base（CLI 未公開）→ issue.target_branch → default。workspace HEAD が base_sha に記録される。
lh pr create同じ順序。--base は workspace より優先する逃げ道として維持。
worktree provisioningPR の base_ref / base_sha から loophub/pr-<m> を fork。
並行 attempt--new-attempt は先行 PR の base_sha を継承し同じ fork 元で比較。
merge / conflict / workflowすべて pull.base_ref を読み、workspace branch への merge と前進に対する conflict sweep が既存動作。
  1. workspace セクションの New issue からは target_branch = workspace ブランチ を書く。以降の base 決定は既存経路。
  2. fork 元は build 時点の workspace HEAD。後から workspace が進んでも既存 PR の base_sha は動かさず、conflict sweep と commits_ahead に委ねる。

対象外

workspace ブランチから default ブランチへの出荷マージは #1352 の対象外。

互換性・責務境界

クリーンスレート前提

#1352 の方針により後方互換・データ移行は考慮しない。既存 issue / PR / default flow の互換維持は目標にせず、既存 row の migration/backfill も既存 branch adopt も行わない。registry が空なら repo top は default section のみ。
