3parent — reconcile ループとして書き直し、手続きは CLI へ

parent(316 行)は watcher protocol・injection 手順・cost interrupt・effect receipt という 決定的な手続きの記述が過半を占める。削り方は 2 段: まず文書構成をゴールへの reconcile ループに変え、次に残った手続きを CLI に吸収する (「プロンプトは判断ポリシー、手続きは CLI」— cli/ thin / core/service の方針と同型)。

構成: ゴールへ reconcile するループとして書く

現行 contract は既に「event は wake だけを担い、判断は domain state で行う」と宣言している。 これは level-triggered な reconciliation の思想そのものだが、文書の構造は event 種別ごとの手順書 (edge-triggered な playbook の羅列)になっており、思想と構成が食い違っている。 同じ「観測してから判断せよ」を event の数だけ再説明しているのはこのため。 ゴール状態を先に定義し、「現状をチェック → 足りないものを確認 → 子を必要に応じて動かす」の ループとして書き直す。

この構成変更だけで、次が構造的に消える(文言編集のみ、コード不要):

  • event 別の節が「gap への翻訳 1 行」に潰れる。merge conflict / GitHub feedback / 人間の追加指示 → 「満たすべき要求が増えた → deliver」。out-of-band review → 「未対応 feedback がある → review id を deliver」。以後は同じ gap 表に従うだけ。
  • replay / at-least-once の注意書きがほぼ消える。毎回観測から判断するので event の replay は無害。durable receipt が要るのは edge-triggered な副作用(Esc・人間確認・通知)だけになり、「Interrupts」節に隔離できる。
  • 新しい event 種別を足しても prompt が伸びない。event は wake に過ぎないため。

前提を強める CLI 変更として、lh workflow step status を完全な observed-state 文書に することを推奨(hold 状態・rework count・未対応 out-of-band review・pending receipt を含める)。 現状これらの一部は event payload でしか届かず、そこだけ event が事実を運んでしまっている。 なお cost interrupt の Esc・人間確認・通知は観測から再導出できない一回性の副作用なので、 reconcile に無理に載せず「Interrupts」として外に置くのが正しい。

遷移判断そのものを CLI へ: lh workflow next

reconcile 構成にすると gap → action の対応は決定的な分類になり、LLM がプロンプト内の表を 読んで判断する必要すらなくなる。判断を core の pure module(例 core/workflow/reconcile.ts)に 移して CLI として公開する — 次に何をすべきかはコマンドが教えてくれる。 

lh workflow next --repo '<repo>' --run <run> --json
→ { "action": "launch_execute" | "advance_and_verify" | "request_rework"
     | "deliver" | "wait" | "escalate" | "ask_human",
    "reason": "<観測事実に基づく説明>", "review_id": 12, ... }
  • 副作用なし・冪等の advisory。入力は observed state だけで、何度呼んでも同じ答え。transition command は従来どおり別に実行する。
  • parent に残る判断は自然言語の生成だけ。無進捗時の follow-up 文、escalation の要約、GitHub feedback を読んで要変更かを決める判断。next はそれらを deliver(文面は parent が書く)として返し、中身は書かない。
  • AGENTS.md の責務分割と同型。pure な decisioning は core module へ。gap 表が unit test 可能になり、判断ロジックの変更が contract 文言の変更から独立する。人間の診断ツール(「この run は何を待っているのか」)にもなる。
  • 決定的 parent への移行路。将来は worker が next を呼び、NL 不要な action を自動実行、NL が必要なときだけ LLM を起こす。LLM parent は「next が要求したときだけ動く部品」へ縮退していく。
  • 注意: 判断の二重化を避ける。next 導入後は contract から gap 表を削除し、「next に従う。各 action の実行方法は次のとおり」だけを残す。prompt と code の両方に判断表があると、食い違ったときにどちらが正か曖昧になる。
  • polling も内包できる(next --watch)。reconcile 化により event cursor は「正しさの機構」から「wake の機構」に格下げされる — action 実行前に parent が停止しても、再起動後の next が同じ state から同じ action を返すため、ack を parent に見せる理由が消える。observed state の完全化(Issue 4)を前提に、event 受信・cursor 管理・観測・判断を blocking 形 next --watch に畳むと、parent の loop は「next --watch を background task で開始 → 起きたら action を実行 → 繰り返し」の 3 行になり、watcher protocol・ack・replay の記述が contract から完全に消える。一回性の副作用(Esc・通知・escalation comment)の二重発火だけは actuator 側の effect receipt で guard し続ける。

6contract 執筆の house rules(再発防止)

  • ゴール → 観測 → gap → action の reconcile 形で書く。event 種別ごとの手順羅列は、観測から再導出できない一回性の副作用(Interrupts)に限る。
  • 存在するものだけを書く(as-built 原則)。「〜はありません」が必要になったら、それは移行説明であり contract の外に置く。
  • 1 規則 1 記載。冒頭の原則に一度書き、各節で繰り返さない。
  • 決定的な多段手続きが現れたら CLI に吸収するサイン。プロンプトには「いつ使うか」だけ残す。
  • CLI が構造的に防げる誤りは書かない。誤操作は non-zero + 誘導メッセージで返す(ack の cursor 照合、--expected-limit の CAS などは既にそう)。
  • why は docs へ、what だけ contract へ。削った設計意図は docs/workflow.ja.md に移してから消す。

やらないこと・リスク

  • コアループと稀 event playbook の文書分割・遅延ロードはしない。参照解決という機構が増え、単一文書の可搬性が落ちる。単一文書のまま頻度順に並べる方が simplest correct。
  • 防御文言の一括削除はしない。個々の禁止事項(pane run Escape の罠、idle detection 禁止など)は過去の実障害由来の可能性がある。「CLI 側の強制に置換してから削る」を原則にし、各 PR の acceptance criteria に「削った防御が CLI の強制に置換されているか」を入れる。由来は git log -p core/workflow/contracts/ で確認できる。
